## 0. 第七轮结论（**此前第五轮的"框架级缺陷"判断作废**）

用户的三个关键描述把方向彻底扭转：

| 用户描述                       | 含义                                    |
| ------------------------------ | --------------------------------------- |
| "残留**是会消失的**不是一直留" | **瞬态** 250~500ms —— 不能靠轮询抓      |
| "残留是**点开的卡片**"         | 内容 = 卡片快照 → 指向我的**代理 View** |
| "**钉在原地不动**"             | 位置固定 = 某个静止图层                 |

前两条合计指向"代理 View 没被摘掉"，第三条确认它不跟手。

**真机抓到的决定性日志**（`22:52:45`，连续"进详情 → 立刻返回"）：

```
22:52:45.065  onAnimationStart isOpen=true
22:52:45.395  mergeAnimation currentId: 8, mReverseToActivityA: true   ← 返回向被合并
22:52:45.918  onAnimationEnd  isOpen=true                             ← 只有 OPEN 结束
```

**框架把返回向合并进了下一次启动向，`onAnimationEnd(isOpen=false)` 永远不会到达。**

而原实现的摘除是：

```kotlin
if (!isOpen) { removeProxy() }     // ← 只在返回向结束时摘
```

于是这条路径上**代理 View 永远不被摘除** —— 它是挂在 `MainActivity.decorView`
上的一个 `ImageView`（z 序在内容之上、位置用 `img.layout()` 钉死在卡片矩形），
**静止、不跟手、内容是刚点开的那张卡**：与用户三条描述**逐字吻合**。

### 为什么此前几轮没找到

- 我一直在**事后**轮询 `dumpsys`，而残留只活 250~500ms（`dumpsys` 单次实测 161ms）
  → 永远只能抓到"已经消失的残骸"，于是错误地推断成"框架级泄漏"；
- `mergeAnimation` 只在"动画未播完就再次操作"时出现，
  常规一轮往返（等它播完）**不会触发**，所以我早期的验证全是绿的。

## 1. 修复（第七轮）

| 改动                                                   | 理由                                                                                            |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 启动向结束 → 代理置 **`INVISIBLE`**（不摘）            | 保留在树上供 CLOSE 取几何（**避开 §S0「坑 B」**），同时让它**不再显示任何像素** —— 残留窗口消失 |
| 返回向结束 → 摘除（原有）                              | 落点已用毕，摘除无害                                                                            |
| 新增 **`PROXY_HARD_TIMEOUT_MS = 1500`** 硬超时兜底摘除 | **不依赖任何回调**；实例比对防误杀。覆盖"回调全都不来"的一切异常路径                            |
| 删掉 `if (!isOpen)` 的清理分支                         | 它默认"返回向一定有始有终"，而实测合并不保证这一点                                              |

**关键设计取舍**（避免用一个降级换另一个）：
第七轮先试过"任何动画结束都 `removeProxy()`"，但那会**直接触发坑 B**
（代理在 CLOSE 开始前被摘 → 框架 `view not attach` → 返回退化成 alpha 淡出）。
最终方案把"**能不能看见**"与"**在不在树上**"分开处理 —— 两个问题同时解决。

## 3. 方法论教训（三条，都是花钱买的）

1. **瞬态现象不能用轮询取证** —— 要么录屏逐帧，要么用动画缩放（10x）
   把窗口拉长；`dumpsys` 161ms 对 250ms 的现象不可靠。
2. **`dumpsys SurfaceFlinger` 必须同时读 `ownerPid`/`uid`/`bounds`/`reachable`**，
   并与 `ps -A` 对照判断进程存活 —— 否则会把历史孤儿层当成新 bug。
3. **任何"等某个回调"的清理都要有硬超时兜底** —— 框架的 `mergeAnimation`
   证明回调并不保证到达。

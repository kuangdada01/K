# 服务器目录重命名方案：`/var/www/shuangchenyue` → `/var/www/k`

> 适用服务器：shuangchenyue（root 登录）
> 目的：本地项目目录已改名为 `k`（`E:\资料\项目\k`），远程部署目录同步改为 `/var/www/k`，协调 nginx + PM2 + 重启顺序，全程可回滚。
> 原则：**只改磁盘路径，不改域名/server_name；任何一步都不删除旧数据，回滚 = 反向 rename。**

---

## 1. 现状评估（结论先行）

### 1.1 服务器端引用点（全部需要处理）

| 引用位置 | 现状 | 需要做什么 |
|---|---|---|
| nginx site 配置 | **实测**：`sites-enabled/shuangchenyue` 是普通文件（非软链），且与 `sites-available/shuangchenyue` 内容**不一致**（enabled 多 `/api/voice/ws` 块）；`root /var/www/shuangchenyue/client/dist`，`server_name _` 默认站；`www.kuangdada.top` 站点只 proxy、不涉及路径 | 改 **sites-enabled/shuangchenyue**（生效份）→ 可选同步 sites-available → `nginx -t` → `systemctl reload nginx` |
| `server/node_modules/@kuangdada/shared` | **实测**：服务器上是**绝对路径符号链接** `-> /var/www/shuangchenyue/shared`（不是相对链接） | 改名后链接悬空，重启 PM2 时 `require('@kuangdada/shared')` 会失败 → 必须**重建链接** `ln -sfn /var/www/k/shared /var/www/k/server/node_modules/@kuangdada/shared`（或重跑 `npm install --omit=dev`） |
| PM2 `kuangdada-server` | **实测**：`script path=/var/www/shuangchenyue/server/dist/index.js`、`exec cwd=/var/www/shuangchenyue/server`、online 15h、node v20.20.2 / pm2 7.0.3 | 必须 **delete 旧进程** → 到新目录 **重新 start** → `pm2 save`（不能只 `pm2 restart`，否则脚本路径失效） |
| 其他潜在引用 | **实测**：crontab / systemd / init.d / supervisor **无** `shuangchenyue` 引用，仅 `/root/.npm` 历史日志（无害）；`.env` 无路径值 | 无需处理，改名后扫尾时再 grep 一遍确认即可 |

### 1.2 本地代码侧（已确认无需改业务代码）

- `server/src/config.ts`：所有 PATHS（`uploads / books / k.db / clientDist / music / .env`）均由 `SERVER_ROOT = path.join(__dirname,'..')` 推导，**没有硬编码绝对路径** → 目录改名后只要重启进程，全部自动跟随新路径，零代码改动。
- `server/ecosystem.config.js`：dotenv 读取 `path.join(__dirname,'..','.env')` → 自动跟随到 `/var/www/k/.env`。
- `deploy.ps1`（第 10 行）：`$REMOTE_DIR = "/var/www/shuangchenyue"` → **必须同步改为 `/var/www/k`**，否则下次部署会建出两个目录。
- `deploy.py` / `deploy-probe*.py`（本地未入库，含凭据，目标为旧服务器 `120.25.100.193` / `/var/www/kuangdada`，`LOCAL_ROOT` 仍是 `E:\资料\项目\kuangdada`）：属于遗留脚本；若不再使用可忽略，若仍要用需一并更新。

### 1.3 数据安全性评估

- `k.db(WAL) / uploads / books / client/public/music` 都是目录内普通文件；`mv` 在同分区内是**原子 rename（只改 inode 名）**，断数据风险极低。
- 只要**先停 PM2 再 rename**，停机期间无写入，WAL 三件套（`k.db / k.db-wal / k.db-shm`）随目录一起移动即保持一致，无需手动 checkpoint。
- 全程不 `rm`、不覆盖旧目录 → 回滚就是反向 `mv`，天然安全。

### 1.4 实测确认（2026-08-25 对 120.25.100.193 只读探测）

- `/var/www` 当前只有 `shuangchenyue`；`/var/www/k` 与 `/var/www/kuangdada` 均不存在，**目标名无冲突**。
- shared 链接是**绝对路径符号链接**，改名后必悬空（见 1.1）；client 目录**无 node_modules**，只有 dist 产物 → 本地"Vite/tsbuildinfo 缓存"坑在服务器**不触发**。
- PM2 `script path` / `exec cwd` 均指向 `/var/www/shuangchenyue/...`，当前 online；node v20.20.2、pm2 7.0.3。
- nginx：`sites-enabled/shuangchenyue` 为**普通文件**且与 sites-available **内容不一致**；站点 `server_name _`（默认站）；`www.kuangdada.top` 站不涉及路径。
- cron / systemd / init.d / supervisor **无** `shuangchenyue` 引用；仅 `/root/.npm` 历史日志（无害）；`.env` 无路径值。
- `/var/www` 与根同分区（`/dev/vda3`，40G/31G 可用）→ **mv 原子改名可行**。
- 当前服务正常：page(200)、health(200)。

## 2. 策略选择（评估）

- **A. 一步改名 + 全配置更新（推荐最终态）**：`mv` 后立刻改 nginx、重启 PM2，随后全盘清除旧名引用。改动集中、结果干净。
- **B. 符号链接过渡（求稳方案）**：`mv` 为新名后建软链 `ln -s /var/www/k /var/www/shuangchenyue`，nginx/PM2 可暂时不改也能继续工作，逐步替换、观察后再删软链。适合首次执行、想最小化停机或担心有遗漏引用。
- **推荐：以 A 为主，借用 B 的软链做观察期兜底**——执行时同步建占位软链，24–48h 观察期结束后删掉。这样即使哪个角落漏改了一个引用，软链也能兜住，不会直接 404。

## 4. 正式执行（停机 → 改名 → nginx → PM2）

### Phase 1 停机（先停后改，避免运行中路径漂移）

```bash
pm2 stop kuangdada-server
pm2 status                       # 确认 stopped
sleep 3
ls -lt /var/www/shuangchenyue/server/uploads | head   # 确认无新写入
```

### Phase 2 改名（瞬时，秒级）

```bash
mv /var/www/shuangchenyue /var/www/k

# 验证结构完整
test -d /var/www/k/server/dist && echo "server/dist OK"
test -f /var/www/k/server/k.db && echo "k.db OK"
test -d /var/www/k/server/uploads && echo "uploads OK"
test -d /var/www/k/client/dist && echo "client/dist OK"
test -f /var/www/k/.env && echo ".env OK"

# 重建 @kuangdada/shared 符号链接（实测为绝对链接，改名后必悬空；重启 PM2 前必须做）
ln -sfn /var/www/k/shared /var/www/k/server/node_modules/@kuangdada/shared
readlink -f /var/www/k/server/node_modules/@kuangdada/shared   # 期望 /var/www/k/shared
# （或直接重跑 npm install --omit=dev 重建链接）

# 观察期占位软链（可选，推荐；与上面的 shared 链接不同，这是目录级软链）
ln -s /var/www/k /var/www/shuangchenyue
```

### Phase 3 nginx

```bash
# 定位（通常是 sites-available 里的文件）
grep -rln "shuangchenyue" /etc/nginx/

# 备份（实测：sites-enabled/shuangchenyue 是普通文件且与 sites-available 内容不一致，生效配置在 enabled 那份）
cp /etc/nginx/sites-enabled/shuangchenyue /root/nginx-sites-enabled-shuangchenyue.bak-$(date +%F)

# 替换生效配置；sites-available 内容不同（缺 /api/voice/ws 块），可选一并同步
perl -pi -e 's#/var/www/shuangchenyue#/var/www/k#g' /etc/nginx/sites-enabled/shuangchenyue
[可选] perl -pi -e 's#/var/www/shuangchenyue#/var/www/k#g' /etc/nginx/sites-available/shuangchenyue

nginx -t && systemctl reload nginx    # 纯路径变更，用 reload 不断开现有连接

# 验证无残留
nginx -T 2>/dev/null | grep -c "shuangchenyue"     # 期望 0
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/     # 前端 200
```

### Phase 4 PM2

```bash
# 清掉旧进程定义（dump 里仍是旧绝对路径，必须 delete 重建，不能只 restart）
pm2 delete kuangdada-server

# 从新路径启动
cd /var/www/k/server
pm2 start ecosystem.config.js
pm2 save                                # 更新 dump.pm2，开机 resurrect 自动用新路径

# 验证指向新路径
pm2 describe kuangdada-server | grep -E "script|cwd|status|uptime"
# 期望: .../var/www/k/server/dist/index.js  /var/www/k/server  online
```

### Phase 5 业务验证

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3000/api/health   # 200
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/                  # 200
# 若配了域名，再验 Host：
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: <你的域名>" http://127.0.0.1/
```

浏览器检查：登录、发一个带图帖子（确认新图落到 `/var/www/k/server/uploads/...` 且可访问）、音乐列表、图书列表、私信图片、管理后台。

## 6. 回滚预案（Rollback）

**触发条件**：`nginx -t` 不通过（未 reload）、新路径结构验证失败、启动后 500/404、健康检查失败、PM2 起不来、业务功能异常。

**因为全程没有删除/覆盖任何数据，回滚 = 反向 rename + 还原 nginx + 重启 PM2：**

```bash
# 1) 停掉新进程
pm2 stop kuangdada-server 2>/dev/null || pm2 delete kuangdada-server 2>/dev/null || true

# 2) 先解除占位软链（若建了），再反向改名（顺序不能反：mv 目标已存在会报错）
rm -f /var/www/shuangchenyue    # 软链时 rm 只删链接，不动真实目录
mv /var/www/k /var/www/shuangchenyue

# 3) 还原 nginx 配置（用 Phase 0 快照最稳）
cp /root/nginx-before-rename.conf /etc/nginx/sites-available/<站点配置>
nginx -t && systemctl reload nginx

# 4) 从旧路径启动
cd /var/www/shuangchenyue/server
pm2 start ecosystem.config.js
pm2 save

# 5) 验证（同 Phase 4/5），并确认 k.db/uploads 完好
pm2 describe kuangdada-server | grep -E "script|cwd|status"
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3000/api/health
ls -la /var/www/shuangchenyue/server/k.db*
```

回滚后复盘：记录失败发生在哪一步（改名？nginx？PM2？），确认原因后再决定重试还是沿用原目录。

## 7. 风险清单与规避

| 风险 | 规避 |
|---|---|
| 运行中进程的文件句柄/后续写入漂移 | **先停 PM2 再 mv**，改名后必须重启（不能只 reload） |
| 只 `pm2 restart` 导致脚本路径失效 | 必须先 `pm2 delete` 旧定义，再到新目录 `pm2 start`，最后 `pm2 save` |
| GNU `sed -i` 断开 sites-enabled 软链 | 用 `perl -pi` 或编辑 sites-available 原件后 `ln -sfn` 重建 |
| 漏改某处引用导致 404 | 占位软链兜底 + 全盘 grep 扫尾 + 观察期 |
| 回滚时 `mv` 目标已存在报错 | 回滚脚本先 `rm -f` 软链，`mv` 前确认目标不存在 |
| 停机造成短暂不可用 | 重命名是秒级操作，停机窗口 ≈ PM2 重启耗时；建议低峰执行 |
